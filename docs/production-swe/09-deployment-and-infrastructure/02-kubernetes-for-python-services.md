# 02 — Kubernetes for Python Services

## Why Kubernetes for Python Applications

Running a Python service on a single server works until the server goes down, traffic spikes, or a bad deploy takes out the whole application. Kubernetes (K8s) solves the operational problems that become unavoidable at scale:

- **Self-healing**: pods that crash are automatically restarted; nodes that fail have their workloads rescheduled
- **Declarative deployments**: the desired state is expressed in YAML; the control plane reconciles reality toward it continuously
- **Zero-downtime updates**: rolling deploys replace pods one at a time, keeping the service available
- **Resource isolation**: requests and limits prevent one misbehaving service from starving neighbours

This file covers the objects and configuration patterns specific to deploying Python services — not Kubernetes administration or cluster setup.

## 1. Core Objects

### Deployment

The primary object for running stateless applications. A `Deployment` manages a `ReplicaSet`, which manages `Pods`.

```yaml
# k8s/deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: feature-pipeline
  namespace: production
  labels:
    app: feature-pipeline
    version: "2024.07.1"
spec:
  replicas: 3
  selector:
    matchLabels:
      app: feature-pipeline
  template:
    metadata:
      labels:
        app: feature-pipeline
        version: "2024.07.1"
    spec:
      # Spread pods across nodes for availability
      topologySpreadConstraints:
        - maxSkew: 1
          topologyKey: kubernetes.io/hostname
          whenUnsatisfiable: DoNotSchedule
          labelSelector:
            matchLabels:
              app: feature-pipeline

      containers:
        - name: feature-pipeline
          # Always reference by SHA or version tag — never :latest
          image: ghcr.io/your-org/feature-pipeline:a3f2b1c
          ports:
            - containerPort: 8080
          envFrom:
            - configMapRef:
                name: feature-pipeline-config
            - secretRef:
                name: feature-pipeline-secrets
          resources:
            requests:
              cpu: "250m"
              memory: "256Mi"
            limits:
              cpu: "1000m"
              memory: "512Mi"
          securityContext:
            runAsNonRoot: true
            runAsUser: 1001
            readOnlyRootFilesystem: true
            allowPrivilegeEscalation: false
            capabilities:
              drop: ["ALL"]
          volumeMounts:
            - name: tmp
              mountPath: /tmp

      volumes:
        - name: tmp
          emptyDir: {}
```

### Service

A stable IP and DNS name in front of the pod set. Pods are ephemeral; Services are not.

```yaml
# k8s/service.yaml
apiVersion: v1
kind: Service
metadata:
  name: feature-pipeline
  namespace: production
spec:
  selector:
    app: feature-pipeline
  ports:
    - name: http
      port: 80
      targetPort: 8080
  type: ClusterIP  # Internal-only; use Ingress for external access
```

## 2. Resource Requests and Limits

Resources must be defined. Without them, pods compete for node resources with no constraints, causing unpredictable degradation.

```yaml
resources:
  requests:         # Guaranteed allocation — scheduler uses this for bin-packing
    cpu: "250m"     # 0.25 vCPU
    memory: "256Mi"
  limits:           # Hard cap — exceeding this triggers throttling (CPU) or OOM kill (memory)
    cpu: "1000m"    # 1 vCPU
    memory: "512Mi"
```

**CPU throttling vs. OOM kill**:
- When a container exceeds its CPU limit, the kernel throttles it — the process slows but keeps running. CPU limits are often set conservatively to prevent runaway processes from affecting neighbours.
- When a container exceeds its memory limit, the kernel kills the process with OOM (Out of Memory). Memory limits should be set based on observed peak usage with a safety margin (e.g., observed peak × 1.5).

**Sizing for ML services**:

| Workload | CPU request | Memory request | Notes |
|----------|-------------|----------------|-------|
| FastAPI API server (no model) | 100–250m | 128–256Mi | Mostly I/O bound |
| FastAPI + small sklearn model | 250–500m | 256–512Mi | Model loaded at startup |
| FastAPI + large transformer | 500m–2 | 2–8Gi | Consider GPU nodes |
| Background worker | 500m | 512Mi | CPU burst on processing |

Run `kubectl top pods` in staging under load to calibrate actual consumption before setting production limits.

## 3. Health Probes

Three distinct probes, each with a different semantic. Misusing them causes unnecessary restarts and obscures the true cause of failure.

### Probe Semantics

| Probe | Question | Failure consequence |
|-------|----------|---------------------|
| **startupProbe** | Has the app finished starting? | Liveness and readiness probes are disabled until it succeeds |
| **livenessProbe** | Is the process still alive? | Pod is killed and restarted |
| **readinessProbe** | Can the pod serve traffic right now? | Pod removed from Service endpoint list |

### Implementation in FastAPI

```python
# src/feature_pipeline/api/health.py
import asyncio
from fastapi import APIRouter, Response
from feature_pipeline.storage import redis_client, db_pool
from feature_pipeline import __version__

router = APIRouter(tags=["health"])

@router.get("/health/live")
async def liveness() -> dict[str, str]:
    """
    Minimal liveness check. Returns 200 if the process is alive.
    Never check external dependencies here — a slow DB should not restart the pod.
    """
    return {"status": "alive", "version": __version__}


@router.get("/health/ready")
async def readiness(response: Response) -> dict[str, str]:
    """
    Dependency-aware readiness check.
    Returns 503 if the pod cannot serve traffic (dependencies not reachable).
    """
    checks: dict[str, str] = {}
    healthy = True

    try:
        await asyncio.wait_for(redis_client.ping(), timeout=1.0)
        checks["redis"] = "ok"
    except Exception as exc:
        checks["redis"] = f"error: {exc}"
        healthy = False

    try:
        async with db_pool.acquire() as conn:
            await asyncio.wait_for(conn.fetchval("SELECT 1"), timeout=1.0)
        checks["postgres"] = "ok"
    except Exception as exc:
        checks["postgres"] = f"error: {exc}"
        healthy = False

    if not healthy:
        response.status_code = 503

    return {"status": "ready" if healthy else "degraded", "checks": checks}
```

### Probe Configuration in the Deployment

```yaml
containers:
  - name: feature-pipeline
    startupProbe:
      httpGet:
        path: /health/live
        port: 8080
      failureThreshold: 30    # Allow up to 30 × 10s = 5 minutes to start
      periodSeconds: 10       # (for large model loading scenarios)

    livenessProbe:
      httpGet:
        path: /health/live
        port: 8080
      initialDelaySeconds: 5
      periodSeconds: 15
      failureThreshold: 3     # Restart after 3 consecutive failures
      timeoutSeconds: 5

    readinessProbe:
      httpGet:
        path: /health/ready
        port: 8080
      initialDelaySeconds: 5
      periodSeconds: 10
      failureThreshold: 3
      timeoutSeconds: 5
      successThreshold: 1
```

**Common mistake**: putting a `readinessProbe` check on `/health/live`. If the database goes down, this causes all pods to be removed from the Service — the API becomes completely unavailable. The liveness probe should be a pure in-process check.

## 4. Rolling Update Strategy

```yaml
spec:
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0  # Never reduce below the desired replica count
      maxSurge: 1        # Allow one extra pod during the update
```

With `replicas: 3`, `maxUnavailable: 0`, and `maxSurge: 1`:

```
Before: [v1] [v1] [v1]
Step 1: [v1] [v1] [v1] [v2]   ← surge pod starts; waits for readiness
Step 2: [v1] [v1]      [v2]   ← one v1 terminated (v2 ready)
Step 3: [v1]      [v2] [v2]   ← another v1 terminated
Step 4:       [v2] [v2] [v2]  ← last v1 terminated
```

This guarantees zero downtime: at no point does the total number of ready pods drop below 3.

## 5. PodDisruptionBudget

A PDB protects availability during voluntary disruptions: node drain, cluster upgrades, `kubectl delete pod`.

```yaml
# k8s/pdb.yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: feature-pipeline-pdb
  namespace: production
spec:
  selector:
    matchLabels:
      app: feature-pipeline
  minAvailable: 2  # Or use maxUnavailable: 1
```

Without a PDB, `kubectl drain node` can evict all pods simultaneously. With `minAvailable: 2` and 3 replicas, no more than one pod is evicted at a time.

## 6. HorizontalPodAutoscaler

Scale pod count based on observed load. Two flavors: CPU-based (simple) and custom metrics (Prometheus-based).

### CPU-Based Scaling

```yaml
# k8s/hpa.yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: feature-pipeline-hpa
  namespace: production
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: feature-pipeline
  minReplicas: 3
  maxReplicas: 20
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70  # Scale when CPU exceeds 70% of request
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 300  # Prevent thrashing: wait 5 min before scaling down
      policies:
        - type: Percent
          value: 25
          periodSeconds: 60  # Scale down at most 25% of pods per minute
    scaleUp:
      stabilizationWindowSeconds: 0   # Scale up immediately
      policies:
        - type: Percent
          value: 100
          periodSeconds: 30
```

### Custom Metrics Scaling (Prometheus Adapter)

For ML serving, request queue depth or feature store hit rate is a better scaling signal than CPU.

```yaml
# Requires prometheus-adapter configured in the cluster
metrics:
  - type: Pods
    pods:
      metric:
        name: http_requests_per_second
      target:
        type: AverageValue
        averageValue: "100"  # Target 100 req/s per pod
```

The Prometheus adapter bridges the Kubernetes metrics API to a Prometheus query, allowing the HPA to scale on any metric the service exposes.

## 7. Helm Charts

Helm templates Kubernetes manifests, enabling environment-specific configuration via values files without duplicating YAML.

### Chart Structure

```
charts/feature-pipeline/
├── Chart.yaml
├── values.yaml          # Defaults — checked into Git
├── values.staging.yaml  # Staging overrides
├── values.prod.yaml     # Production overrides
└── templates/
    ├── deployment.yaml
    ├── service.yaml
    ├── ingress.yaml
    ├── hpa.yaml
    ├── pdb.yaml
    └── _helpers.tpl
```

### Values File

```yaml
# values.yaml
image:
  repository: ghcr.io/your-org/feature-pipeline
  tag: "latest"   # Overridden in CI with the actual SHA
  pullPolicy: IfNotPresent

replicas: 2

resources:
  requests:
    cpu: "250m"
    memory: "256Mi"
  limits:
    cpu: "1000m"
    memory: "512Mi"

env:
  LOG_LEVEL: "INFO"
  LOG_FORMAT: "json"

autoscaling:
  enabled: true
  minReplicas: 2
  maxReplicas: 10
  targetCPUUtilization: 70
```

### Safe Deployment

```bash
# Deploy with --atomic: rolls back automatically if the upgrade fails health checks
helm upgrade feature-pipeline ./charts/feature-pipeline \
    --install \
    --namespace production \
    --values ./charts/feature-pipeline/values.prod.yaml \
    --set image.tag="${GITHUB_SHA}" \
    --wait \
    --timeout 5m \
    --atomic
```

`--atomic` + `--wait` together: Helm waits for all pods to reach Ready state. If they don't within the timeout, it rolls back to the previous release automatically — a critical safety net for deployments that fail readiness checks silently.

## Summary

| Concern | Decision |
|---------|----------|
| Image reference | Always SHA or version tag; never `:latest` |
| Resources | Always set both requests and limits |
| Liveness probe | Pure in-process check: never checks external dependencies |
| Readiness probe | Checks all critical dependencies; returns 503 if unhealthy |
| Startup probe | Required for services with slow starts (model loading) |
| Rolling update | `maxUnavailable: 0`, `maxSurge: 1` for zero-downtime |
| Pod disruption | PDB with `minAvailable: N-1` for all production services |
| Autoscaling | HPA on CPU (default) or custom Prometheus metric (ML workloads) |
| Helm deploy | `--atomic --wait --timeout 5m` for automatic rollback on failure |
